# راه‌اندازی روی سرور — alefcapital.ir

---

## خلاصه تصمیم

سایت در این مرحله **کاملاً ایستا** است: ۱۸ فایل HTML. برای ۱۰۰ کاربر این تقریباً هیچ باری نیست.

| | انتخاب | چرا |
|---|---|---|
| وب‌سرور | **Caddy** | HTTPS خودکار می‌گیرد و خودکار تمدید می‌کند. یک فایل پیکربندی ۳۰ خطی به‌جای nginx + certbot + cron. |
| اجرا | **Docker Compose** | یک دستور بالا می‌آید، روی هر سروری قابل انتقال است. |
| به‌روزرسانی | `git pull && make build` | پوشه `dist/` به‌صورت volume سوار است؛ **نه build مجدد image لازم است، نه restart**. تغییر محتوا در چند ثانیه زنده می‌شود. |
| سرور | ۱ vCPU / ۲GB RAM | برای این حجم بیش از حد کافی است. |

---

## ۱. سرور

یک VPS ساده کافی است. مشخصات پیشنهادی برای شروع:

- **۱ هسته CPU، ۲ گیگ رم، ۲۰ گیگ دیسک**
- اوبونتو ۲۲.۰۴ یا ۲۴.۰۴
- ترجیحاً **دیتاسنتر داخل ایران** — تأخیر شبکه برای کاربر ایرانی مستقیماً روی نرخ تبدیل اثر می‌گذارد

> ⚠️ **سایت را روی سرور الگوریتم معاملاتی بالا نیاورید.**
> یک وب‌سرور عمومی روی ماشینی که الگوریتم و اتصال کارگزاری روی آن اجرا می‌شود،
> سطح حمله را بی‌دلیل باز می‌کند. این دو را جدا نگه دارید.

نصب پیش‌نیازها:

```bash
sudo apt update && sudo apt install -y git make python3 docker.io docker-compose-plugin
sudo usermod -aG docker $USER   # سپس یک بار خارج و دوباره وارد شوید
```

## ۲. دامنه

در پنل ثبت‌کننده دامنه (ایرنیک یا نمایندگی)، دو رکورد A بسازید:

| نوع | نام | مقدار |
|---|---|---|
| A | `@` | آی‌پی سرور |
| A | `www` | آی‌پی سرور |

انتشار DNS معمولاً چند دقیقه تا چند ساعت طول می‌کشد. بررسی:

```bash
dig +short alefcapital.ir
```

> Caddy برای گرفتن گواهی از Let's Encrypt باید روی پورت ۸۰ در دسترس باشد.
> اگر CDN (مثل ابرآروان) جلوی سایت می‌گذارید، **اول بدون CDN بالا بیاورید** تا گواهی گرفته شود،
> بعد CDN را فعال کنید.

## ۳. بالا آوردن

```bash
sudo mkdir -p /srv && cd /srv
git clone <آدرس مخزن شما> alef-capital
cd alef-capital

make build
docker compose -f deploy/docker-compose.yml up -d
```

تمام. چند ثانیه بعد `https://alefcapital.ir` با گواهی معتبر بالاست.

بررسی وضعیت:

```bash
docker compose -f deploy/docker-compose.yml logs -f caddy
```

## ۴. چرخه کار روزمره شما

این مهم‌ترین بخش است، چون قرار است مدام روی سایت کار کنید.

**روی لپ‌تاپ:**

```bash
make serve          # http://localhost:8000 — تغییرات را ببینید
make check          # مطمئن شوید چیزی نشکسته
git commit -am "تغییر قیمت پلن طلا"
git push
```

**روی سرور:**

```bash
./deploy/deploy.sh
```

این اسکریپت `git pull` می‌کند، سایت را می‌سازد، لینک‌ها را چک می‌کند و تمام.
**کانتینر restart نمی‌شود** چون Caddy فایل‌ها را مستقیم از `dist/` می‌خواند.

اگر می‌خواهید این هم خودکار شود، `.github/workflows/deploy.yml` آماده است:
سه Secret (`SSH_HOST`، `SSH_USER`، `SSH_KEY`) در تنظیمات مخزن بسازید و با هر
push روی `main` سایت خودکار منتشر می‌شود.

## ۵. ظرفیت — چرا ۱۰۰ کاربر مسئله نیست

بیایید عدد بگذاریم:

| | مقدار |
|---|---|
| حجم هر صفحه (HTML با CSS داخلی) | حدود ۵۵ کیلوبایت |
| بعد از فشرده‌سازی gzip/zstd | حدود ۱۲ کیلوبایت |
| ۱۰۰ کاربر که **هم‌زمان** یک صفحه باز کنند | حدود ۱.۲ مگابایت |
| پردازش لازم | صرفاً خواندن فایل از دیسک |

یک هسته CPU چند هزار درخواست ایستا در ثانیه سرو می‌کند. ۱۰۰ کاربر هم‌زمان
حتی ۱ درصد ظرفیت این سرور را مصرف نمی‌کند. **گلوگاه شما پهنای باند و تأخیر
شبکه است، نه CPU.**

سه کاری که واقعاً به سرعت کمک می‌کنند (هر سه در `deploy/Caddyfile` تنظیم شده‌اند):

1. **فشرده‌سازی** — ۵۵ کیلوبایت به ۱۲ کیلوبایت
2. **کش دارایی‌ها** — فونت و تصویر یک سال کش می‌شوند، HTML کش نمی‌شود
3. **HTTP/2 و HTTP/3** — پیش‌فرض فعال

بزرگ‌ترین برد سرعت، چیزی است که ربطی به سرور ندارد: **خودمیزبان کردن فونت**
(`make fonts`). فونت از Google Fonts برای کاربر ایرانی می‌تواند چند ثانیه طول بکشد
یا اصلاً نیاید.

## ۶. وقتی API اضافه شد

سایت فعلاً ایستاست، اما داشبوردها به داده زنده نیاز دارند. معماری پیشنهادی:

```
                    ┌─────────────┐
   مرورگر کاربر ───►│    Caddy    │
                    └──────┬──────┘
                     ┌─────┴─────┐
                     ▼           ▼
              dist/ (ایستا)   FastAPI
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
                 Redis      PostgreSQL   خواننده بازار
                (کش ۱s)    (TimescaleDB)  (یک پروسه)
```

**یک نکته که همه‌چیز را عوض می‌کند:** بین API و دیتابیس یک کش Redis با
عمر یک ثانیه بگذارید. آن‌وقت ۱۰۰ کاربر که هر ۵ ثانیه داده می‌گیرند،
حدود ۲۰ درخواست بر ثانیه به API می‌زنند اما فقط **حدود ۱ کوئری در ثانیه**
به دیتابیس می‌رسد. بدون این کش، همان ۲۰ درخواست مستقیم روی دیتابیس می‌نشیند.

قاعده کلی: **یک پروسه از بازار می‌خواند، بقیه از کش می‌خوانند.**
هرگز اجازه ندهید تعداد کاربر روی تعداد درخواست به منبع داده اثر بگذارد.

برای این مرحله:

- سرور را به **۲ هسته / ۴ گیگ رم** ارتقا دهید
- Uvicorn با ۲ تا ۴ worker کافی است
- برای داده لحظه‌ای، SSE ساده‌تر از WebSocket است و برای یک‌طرفه بودن جریان کافی
- بلوک `api.alefcapital.ir` در `Caddyfile` کامنت شده و آماده است

## ۷. پشتیبان‌گیری

در این مرحله فقط دو چیز ارزش نگهداری دارند:

1. **خود مخزن گیت** — کل سایت از آن بازساخته می‌شود
2. **volume به نام `caddy_data`** — گواهی‌های TLS داخلش است

```bash
docker run --rm -v alef-capital_caddy_data:/data -v $(pwd):/backup \
  alpine tar czf /backup/caddy-data.tar.gz /data
```

پوشه `dist/` نیازی به پشتیبان ندارد؛ با یک `make build` دوباره ساخته می‌شود.
